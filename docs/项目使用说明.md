# 夺锦之星 ROS 2 项目使用说明

本文说明 `duojin_ws` 从本地开发、GitHub 同步到机器人工控机编译和运行的完整流程。
所有真机命令默认在 R1 Lite 工控机上执行。

## 1. 项目定位

本项目采用 ROS 2 underlay/overlay 架构：

```text
~/galaxea/install_430
  厂商 SDK underlay
  负责 CAN、HDAS、Mobiman、Joint Tracker、Relaxed IK、相机等底层节点

~/duojin_ws
  赛队 overlay
  负责测试节点、感知、决策、任务编排和后续比赛代码
```

两个目录必须保持物理解耦。不要把赛队源码放入 `install_430`，也不要修改或提交 SDK
文件。`source` 只加载当前 shell 的包和库搜索路径，不会启动 ROS 节点。

## 2. 环境要求

### 本地开发机

- 负责编辑源码、静态检查、Git 提交和推送。
- 没有 ROS 2 Humble 时不能完成 `colcon build` 和真机 ROS 验证，这是预期状态。
- 不要上传本地产生的 `build/`、`install/`、`log/`。

### 机器人工控机

- ROS 2 Humble 安装在 `/opt/ros/humble`。
- 厂商 SDK 位于 `~/galaxea/install_430`。
- 存在 `~/setup_can.sh` 和 `~/can.sh`。
- 项目默认位于 `~/duojin_ws`，脚本也支持从其他位置运行。
- 工控机与机器人 ROS 节点使用一致的 `ROS_DOMAIN_ID`。

## 3. 首次下载项目

如果修复分支还没有合并到 `main`，必须明确克隆对应分支：

```bash
cd ~
git clone --branch agent/fix-dual-ros-workflow \
  git@github.com:nocorn-ops/-World-Humanoid-Robot-Games-for-duojin-stars.git \
  duojin_ws
```

如果该分支已经通过 PR 合并到 `main`，则使用：

```bash
cd ~
git clone \
  git@github.com:nocorn-ops/-World-Humanoid-Robot-Games-for-duojin-stars.git \
  duojin_ws
```

确认当前代码版本：

```bash
cd ~/duojin_ws
git status --short --branch
git log -1 --oneline
```

## 4. 编译赛队工作区

```bash
cd ~/duojin_ws
./scripts/build_robot.sh
```

脚本会依次完成：

1. 检查 `~/galaxea/install_430/setup.bash`；
2. 加载厂商 SDK underlay；
3. 检查 `ros2` 和 `colcon`；
4. 执行 `colcon build --symlink-install`。

编译成功后会生成 `build/`、`install/`、`log/`。这些目录只属于当前工控机，不进入
Git。

只修改 `start.sh`、`stop.sh`、`scripts/*.sh` 或文档时不需要重新运行
`colcon build`；修改 `src/` 中的 ROS 2 包、消息定义或依赖后必须重新编译。

## 5. 一键启动全部运行环境

确认急停可用、机器人周围无人且机械臂工作区没有障碍物，然后执行：

```bash
cd ~/duojin_ws
./start.sh
```

脚本严格按以下顺序运行：

```bash
bash ~/setup_can.sh
bash ~/can.sh
cd ~/galaxea/install_430/startup_config/share/startup_config/script
./robot_startup.sh boot ../sessions.d/ATCStandard/R1LITEBody.d/
```

随后脚本会：

1. 等待 30 秒并检查 `/motion_target/` 话题；
2. 自动关闭 `r1lite_teleop`，进入自主控制模式；
3. 检查底盘、躯干、双臂、双夹爪的控制节点、指令订阅和实时反馈；
4. 检查双 IMU、电池/BMS、头部双目及左右腕相机数据；
5. 确认全部必需链路可以交给自主程序；
6. 加载 SDK underlay 与项目 overlay，进入带 `[duojin]` 提示符的环境 Shell。

整机检查的具体范围如下：

- 控制节点：底盘、躯干、夹爪、末端位姿、Joint Tracker、左右 Relaxed IK；
- 目标输入：底盘、躯干速度/关节、双臂笛卡尔/关节、双夹爪目标话题的订阅者；
- 执行链路：底盘、躯干、双臂、双夹爪的 `/motion_control/*` 到 HDAS 链路；
- 实时反馈：底盘、躯干、双臂、双夹爪、双 IMU、BMS 和双臂末端位姿；
- 视觉设备：头部双目左右彩色流，以及左右腕 RealSense 的彩色和深度流。

`[OK]` 表示该项在线；任意 `[FAIL]` 都会使 `start.sh` 返回非零状态，不会进入
比赛环境 Shell。即使机械臂单独可用，只要其他必需设备未通过，整机启动仍会停止。
这个检查只读取 ROS 图和一帧实时数据，不发布运动命令，也不能替代环境清场和急停。

它不会拉取代码、编译项目或启动比赛 launch。链路检查通过后会自动在
`duojin_arm_api` tmux 会话中启动唯一的机械臂 preview API；新的环境 Shell 已经按顺序
source 好 SDK 和项目，可以直接运行比赛 Python 程序或发送 preview Goal：

```bash
ros2 action list -t | grep '^/duojin/arm/'
```

也可以直接执行机械臂 preview-only 诊断脚本或其他项目 launch：

```bash
./scripts/run_arm_ik_test.sh
ros2 launch <比赛包> <比赛启动文件>
```

输入 `exit` 只退出环境 Shell，不会关闭已经由 tmux 托管的 SDK。完整关闭需要从另一个
终端执行 `~/duojin_ws/stop.sh`。

如果启动失败，先检查厂商 tmux 会话和关键话题：

```bash
tmux list-sessions
source ~/galaxea/install_430/setup.bash
ros2 topic list | grep -E 'motion_target|hdas/feedback|motion_control'
```

不要在 SDK 部分启动失败时手动补启动 Joint Tracker、Relaxed IK 或 HDAS。应先修复
完整 SDK 启动问题，避免出现两份控制器使用不同参数同时运行。

需要单独重新检查整机链路时，执行：

```bash
cd ~/duojin_ws
./scripts/check_robot_control_chains.sh
```

各反馈话题会并行等待，默认超时为 12 秒，因此多个设备离线时不会按设备数量
累加等待时间。

## 6. 可选：单独诊断机械臂控制链

左臂：

```bash
cd ~/duojin_ws
./scripts/start_arm_environment.sh left
```

右臂：

```bash
cd ~/duojin_ws
./scripts/start_arm_environment.sh right
```

检查脚本会加载 `install_430` underlay 和 `duojin_ws` overlay，并确认：

- HDAS 机械臂反馈存在；
- Joint Tracker 节点在线；
- 对应手臂的 Relaxed IK 节点在线；
- 当前末端位姿话题有数据。

该脚本只检查环境，不启动或停止任何厂商节点。它只用于定位单臂问题，不代替
`start.sh` 中的整机链路检查。

## 7. 运行旧 IK 链路诊断（仅预览）

`run_arm_ik_test.sh` 是保留的旧笛卡尔 IK 链路诊断，只允许 preview。
预览模式不会发布运动目标：

```bash
cd ~/duojin_ws
./scripts/run_arm_ik_test.sh
```

右臂预览：

```bash
./scripts/run_arm_ik_test.sh --ros-args -p arm:=right
```

可以改变偏移来检查目标计算，仍不得开启执行：

```bash
./scripts/run_arm_ik_test.sh --ros-args \
  -p delta_x:=0.02 -p delta_z:=0.0
```

禁止向该脚本传入 `execute:=true`。厂商 Relaxed IK 处理 Pose 时会直接
向 `/motion_target/target_joint_state_arm_*` 发布关节目标；项目只能在该副作用
发生后观察 IK 输出，无法在其进入 Joint Tracker 前完成关节限幅。在
IK 输入/输出隔离完成前，Pose 物理执行一律禁用。

比赛程序和新测试应走统一 API：`move_to(..., execute=False)` 或
`move_by(..., execute=False)` 只做 Pose
preview；需要真机运动时，使用第 8 节的 `move_joints` 关节空间路径，不要
用旧 IK 诊断脚本绕过统一安全门。

## 8. 运行统一机械臂 API

首次部署以及任何 `src/` 源码、Action 定义或依赖变更后，先在工控机执行：

```bash
cd ~/duojin_ws
./scripts/build_robot.sh
```

日常使用时，无参数 `./start.sh` 通过完整链路检查后会自动启动一份 preview server，
再进入已加载环境的 `[duojin]` Shell；程序可直接调用。真机关节执行必须先完成清场、
底盘制动、控制权和急停检查，再从完全停止的环境显式启动：

```bash
./start.sh --enable-arm-motion
```

上述参数只是 server 级许可。每个 Action Goal 或 Python 调用还必须再显式
设置 `execute=true`，两道门都打开才会运动；Python 默认 `execute=False` 只 preview。
该许可目前只放行 `move_joints`；`move_to`/`move_by` 物理执行因厂商 Relaxed IK 输出无法在进入
Joint Tracker 前校验而返回 `POSE_EXECUTION_UNSAFE`，完成隔离方案前不得绕过。
真机关节目标必须经过限位、单次变化量和速度验证，然后通过统一
`move_joints(..., execute=True)` 提交；`run_arm_ik_test.sh` 不是关节空间真机入口。

左右臂各有 `move_to`、`move_by` 与 `move_joints` Action，并自动发布
`/duojin/arm/{left,right}/current_pose`。比赛 Python 程序使用
`duojin_robot_interface.arm_client.ArmClient`。新终端必须使用与 SDK 相同的
`ROS_DOMAIN_ID`，并且先 source SDK underlay、再 source 项目 overlay。不要在同一条手臂
运动期间并发新目标；第二个目标会返回 `BUSY`，需先 cancel 并等待旧目标结束。
在 `start.sh` 打开的 shell 中可直接执行
`ros2 run duojin_robot_interface arm_pose_display --ros-args -p arm:=left` 实时查看左臂末端坐标；
Python 使用 `ArmClient.get_pose()` 读一条新鲜位姿。

全部前置检查、精确 Action schema、ROS/Python 示例、停止顺序、错误排查和 L2–L4
验证步骤见 [`runbooks/arm-motion-api.md`](runbooks/arm-motion-api.md)。当前限速、误差和新鲜度
参数是保守工程初值，尚未真机标定；API 不做碰撞规划，软件 hold 也不是急停。

## 9. 底盘与躯干接口

底盘和躯干的详细话题、消息字段、范围与联调结论见
[`r1_lite_interfaces.md`](r1_lite_interfaces.md)。二开的基本边界是：

- 向 `/motion_target/*` 发布标准 ROS 2 消息；
- 从 `/hdas/*` 接收反馈；
- 不直接发布 `/motion_control/*` 的 `MotorControl` 消息；
- 底盘速度命令以约 10 Hz 持续发布，停止时显式发布零速度；
- 自主运动前先解除刹车，任务结束后停止并恢复制动。

## 10. 后续更新

工控机当前分支已经正确配置远端后，可执行：

```bash
cd ~/duojin_ws
./scripts/update_robot.sh
```

该脚本会：

1. 检查工控机工作区是否存在未提交改动；
2. 执行 `git pull --ff-only`；
3. 重新运行 `build_robot.sh`。

注意：它只更新“当前分支”。如果工控机在 `main`，而新代码只存在于功能分支，运行
该脚本不会自动取得功能分支的代码。

## 11. 功能分支没有合并 PR 的影响

提交并推送到功能分支后，即使没有创建或合并 PR，也可以从该分支手动克隆、拉取、
编译和运行。但只要功能分支没有合并进 `main`，就会有以下后果：

1. `main` 不包含该功能分支的更改。
2. 默认克隆仓库得到的是 `main`，不会得到功能分支代码。
3. 已在 `main` 上运行的工控机执行 `git pull` 或 `update_robot.sh`，也不会得到这些更改。
4. GitHub 上没有正式的代码审查、讨论、CI 检查和合并记录。
5. 后续其他修改如果继续基于旧 `main`，可能重新引入旧路径或产生合并冲突。
6. 如果远端功能分支以后被删除且没有合并，团队成员将更难发现和获取该版本。

因此，PR 不是 Git 运行代码的技术前提，但它是把功能分支正式纳入 `main` 的标准入口。
不要依赖文档中的某个历史提交号判断版本，部署前应执行：

```bash
git status --short --branch
git log -1 --oneline
```

在 PR 合并前，工控机必须显式切换到目标功能分支，例如：

```bash
cd ~/duojin_ws
git fetch origin
git switch --track origin/agent/fix-dual-ros-workflow
./scripts/build_robot.sh
```

如果本地已经存在该分支：

```bash
git switch agent/fix-dual-ros-workflow
git pull --ff-only
./scripts/build_robot.sh
```

PR 合并到 `main` 后，推荐工控机重新回到主分支：

```bash
git switch main
git pull --ff-only
./scripts/build_robot.sh
```

## 12. 一键关闭全部 ROS 2 进程

在项目根目录执行：

```bash
cd ~/duojin_ws
./stop.sh
```

脚本会依次：

1. 尽力向底盘发布零速度和制动命令；
2. 调用厂商 `robot_startup.sh kill` 关闭 SDK 和 tmux server；
3. 查找并终止当前工控机用户剩余的 ROS 2 进程；
4. 停止 ROS 2 daemon。

厂商停止命令会关闭当前用户的整个 tmux server。`stop.sh` 不能代替硬件急停。

## 13. 常见故障

### 找不到 `install_430/setup.bash`

确认 SDK 位于当前工控机用户的 `~/galaxea/install_430`，不要改成旧的
`~/galaxea/install`。

### 找不到 `ros2` 或 `colcon`

说明 `install_430` 没有成功加载其 `/opt/ros/humble` underlay，或者工控机缺少完整
Humble 环境。不要在本地无 ROS 的开发机上强行构建。

### 有话题但没有机械臂反馈

检查机器人供电、急停、CAN、HDAS tmux 窗口和 `ROS_DOMAIN_ID`。仅看到话题名称不能
证明硬件控制链正常。

### 环境检查提示缺少 Joint Tracker 或 Relaxed IK

重新检查 `R1LITEBody.d` 的完整启动日志，不要由项目脚本单独启动缺失节点。

### 整机检查显示 `missing node`

对应的 SDK 控制窗口没有成功启动或节点已经退出。优先查看 `mobiman`、`hdas` 和
`system` tmux session 的日志，不要为了让检查通过而重复启动同名控制器。

### 整机检查显示 `no subscriber`

目标话题后面没有控制器，或 `/motion_control/*` 后面没有 HDAS 执行端。这种情况下话题名
可能存在，但命令无法完整到达硬件；应修复 SDK 完整启动，不要绕过检查直接运动。

### 整机检查显示 `no message`

该设备在默认 12 秒内没有产生一帧实时数据。底盘、躯干、机械臂、夹爪、IMU 或 BMS
失败时检查供电、急停、CAN 和 HDAS；相机失败时检查 `/dev/camera_head`、左右
RealSense 序列号文件以及 `hdas` 相机窗口。

### 执行模式提示 `r1lite_teleop` 冲突

确认已退出人工遥操作模式，再执行：

```bash
tmux kill-session -t r1lite_teleop
```

### `update_robot.sh` 拒绝更新

工控机工作区存在未提交修改。先执行 `git status`，确认这些改动的归属；不要直接覆盖
或删除未经确认的真机修改。
